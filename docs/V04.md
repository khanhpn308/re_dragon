# v0.4 — Agent-owned investigation ledger

## Architecture decision

v0.3 implemented a Python REA CLI executor. v0.4 adds the **primary Agent path**:
direct REA MCP calls by Codex/Antigravity + durable investigation state in
the RE Dragon MCP server. There is no second hidden LLM, Python autonomous
planner, or redundant REA MCP subprocess.

## Durable data

A new additive SQLite schema stores:
- investigations (natural language objective, optional local target path and
  SHA-256 pin, Agent name, lifecycle status)
- investigation_steps (Agent-authored ordered milestones, acceptance criteria,
  explicit progress and blockers)
- rea_observations (the Agent's receipt of a REA MCP call: tool name, optional
  REA Evidence ID, digest when observed, caveats and a bounded summary)
- investigation_findings (VERIFIED/INFERRED/UNKNOWN statements linked to one or
  more observation receipts and symbol/address when VERIFY is asserted)
- investigation_events (append-only action log, current timestamps)

Migrations are additive and do not delete v0.3 task leases, binaries or reports.

## Verification model

A0: local target identity, A1: plan exists, A2: all milestones completed,
A3: observations exist, A4: findings exist.
A5: **UNVERIFIED** because the tool data is reported by the Agent and is not
independently cryptographically verified against the REA MCP session.
A6: **REVIEW_REQUIRED** because semantic validity cannot be inferred from a
tool call succeeding. "ready_for_review" means A0–A4 PASS only.

MCP evidence IDs from REA are useful referents but may require same-session
access or exporting/reimporting the original evidence bundle across sessions.
The receipt is not a replacement for raw function evidence, source locations,
coverage or limitations.

## Trust and resource controls

Text lengths, step counts, receipt caveat counts and finding references are
bounded. A VERIFIED-labelled finding must have source observation IDs, a
symbol/address and rationale. Step completion requires at least one linked
observation. All source outputs are untrusted data rather than instructions.

There is no network probing, APK patching, token interception or game-server
communication in this layer. It does not launch Python CLI REA by default.
The legacy executor is still available for migrated projects.

## Current limitations

Not yet a cloud-hosted autonomous Agent. It needs a Codex or Antigravity
session with both MCP servers connected. It does not automatically synthesize
the investigation plan; the LLM Agent does. Receipts cannot independently
authenticate the actual REA tool result without a verified import/bundle
workflow. Real Ghidra integration still requires a live environmental run.
